## 0. 结论速览

1. res 源码里的玩法宇宙是**同一批约 40 个玩法域**在四条技术路线上的四次投影：Nya 线（纯 Python，最完整可玩，`FakeFlashSession` 单类 1,417 个方法）、2012 原版（Java fatjar + MySQL 187 表，战斗执行体缺失）、复刻组线（C# 105 个 `Handle*` + MySQL 84 表）、魔改四家（在 Nya 上做增量）。
2. 从源码中抽离出 **16 个横切实现模式**（§3，M1–M16）：opcode 路由表、双 wire 协议、配置驱动、集中 Tick + pending 队列、日/周/赛季刷新锚、玩法状态机、派生数值链、概率 roll 工具族、经济账本与 escrow、存档分层、时间累积挂机、活动调度、GM 动作直连、特殊技能实体化、竞技镜像、客户端三件套。**任何一个玩法 = 若干模式的组合**。
3. 同一玩法在不同路线上的**模式同构、载体不同**：例如"每日刷新"在 Nya 是 save JSON 里的 `day_key` 三段式刷新函数（v223 `fake_flash_server.py:32230`），在 2012 是 `role_day_arena` 表 + 每日 0 点 Timer 清表（`RoleGiftTask.java.svn-base`），在复刻组是 `character_copy_daily.reset_date` 列 + 事务——模式一样，存储分别是 JSON 文件 / MySQL 行 / MySQL 行。
4. 战斗结算呈现清晰的**代际演进**（§4）：2012 战斗服缺失不可考 → Nya 2.2.0"宣布即扣血"有双扣 bug → 2.2.3 改为**授权-申报两段式 + 客户端声明采信**（v223:4236 `PendingPvpHit`、44125 `_settle_client_pve_claim`）→ 复刻组线独立得出同构结论"视觉先行、伤害确认后才扣血"（gm_feature_mappings `monster.attack.visual`）。
5. 魔改生态扩展玩法只有**六种方法套路**（§6）：类内追加方法、配置面调参、GameData.dat 流改写、FFDec 源级注入/资源替换、RABCDAsm 字节码破解、外挂 HTTP 子系统。tzl→嗯哼→jishui 恰好是"0 级不碰客户端→1 级改脚本换资源→2 级改字节码"的完整台阶。

## 3. 十六个横切实现模式（核心抽取结果）

> 每个模式给出：定义 → 典型玩法 → 各路线对照 → 锚点。**这 16 个模式是 res 源码里所有玩法的"生成语法"**。

### M1 opcode 路由表 + 子 action 二级分发
所有客户端请求经一张字典路由到 handler；复杂玩法在 handler 内再按"首字段 action 编号"二次分发。
- Nya：`op(ClientOpcode.X): self.handle_yyy` 字典 120 项（V223:11498-11618），`_dispatch` 直查 :14192；二级分发如 `handle_item_change` 按枚举拆 ~30 子操作 :53177、`handle_pve_action` :28560。
- 2012：无路由表，`Console.action` 约 30 个 `equals` if-else 分支（`Console.java.svn-base:33-124`）——同一模式的前身形态。
- 复刻组：双层路由（外层 opcode + 内层 GamePacket）+ 105 个 `Handle*` async 方法（DLL 元数据）。
- 客户端对称面：`Client.as`（11,712 行、559 个 `requestXxx`）→ 域 Processor → `PacketCreator` ~100 个包工厂 → `sendPacket`（ML `com\mxw\game\client\Client.as`、`net\client\PacketCreator.as`）。

### M2 双 wire 协议（文本逻辑层 + 二进制原生层）
Nya 线内部逻辑用 `"opcode:field..."` 文本，另有一族 `_send_original_*_text` 函数把文本转 struct 二进制喂给原生 Flash 客户端（V223:57400、57684、`send_original_packet` :13099）。这是"字节级复刻 2012 二进制协议"与"纯 Python 可维护性"之间的妥协层。2012 原版只有二进制（`0xF0 0x02` 头 + 数位和校验 + `pt/uid/action`）；复刻组线用 AMF3。校验体系三样：Nya `crc_hqx(payload)*31+sid` + 256 项解码盒（`ORIGINAL_CLIENT_DECODE_BOX`，versions/2.2.1 `fake_flash_server.py:392-409`）、2012 数位和、复刻组 sa-token（仅 GM 面）。

### M3 配置驱动玩法（数据表分区即玩法参数）
玩法参数全部外置，代码只做引擎。四种数据投影：
- Nya：`GameDataCatalog` 挂 GameData.dat 的 AMF3 分区（Map/Mob/Quest/War/FuBen/Pve/Pk/Huodong/XiuXing/ChengJiu/Card/Mai/LingQi/ShenQi/HunJie/RenJu/Pet/Vip…34 root 分区 + 物品 15 子分区，V223:5387-5460、`ITEM_SECTION_NAMES` :5240）；访问器全为只读方法（`pve_levels` :6130、`copy_wave_plan` :6995）。
- 2012：quest 37 列内联全部奖励、skill 五表、`life_skill_prescription` 配方 4 材料 3 产出、`arena_time` 按周时刻——数值全在 MySQL（`DB/game.sql`）。
- 复刻组：84 表 + Flyway 迁移；且把**GameData 反推结果的 SHA-256 写进每行配置**（`activity_reward_sets.source_gamedata_sha256`、`treasure_box_templates.evidence_key`）——"配置溯源"是复刻组独有增强。
- 编辑器：`ENTITY_TYPES` 26 类实体定义（ED `catalog.py:169-196`），其中 8 类是**无代码运行规则**（game_texts/balance_rules/formulas/activities/automation_events/item_effects/buffs/ui_entries）——官方自己把"改玩法不改码"产品化了。
- 热加载：Nya `EDITOR_RUNTIME` 按 revision 热载、`BALANCE_DEFAULTS` 兜底（V223:5661-5676）；复刻组 `config_reload.reload_flag=1` 轮询重载（JAR + server.log `Auto-reload triggered by DB flag`）；魔改直接改 `editor_runtime_config.py` 的 `BALANCE_DEFAULTS`（jishui 掉落池 108 键，`x2\jishui\...\tools\editor_runtime_config.py:126`）。

### M4 集中 Tick + pending 队列 + 单调时钟
一切"异步要有个期限"的交互都是**入队 + deadline + tick 清理**。Nya 有单一 `_runtime_tick`（V223:35135-35350）按固定顺序驱动 30+ 子系统；战斗三队列（`pending_pvp_hits` :41024、`pending_pve_settlements` :40230、`pending_monster_kills` :45040）；经脉点脉延迟爆炸 `PendingMaiExplosion` :4143；掉落过期 `_expire_map_drops` :46433；HUD 补发队列 `pending_*_replay_at`（quest :35236、LIANZHAN :38022）。2012 的对应物是 SQL-over-socket 写队列（dataServer 单线程每 5s 批量 1000 条，`ServerHandle.java.svn-base:29-61`）与每 5 分钟排行榜 Timer。复刻组对应物是"视觉先行、伤害协议确认后才扣血"的确认链（JAR V3 `monster.attack.visual` 行）。

### M5 日/周/赛季刷新锚（day_key/week_key/season_key）
限次玩法共用一个三段式：`key 不同则重置字段`。
- Nya：次日零点 `_seconds_until_tomorrow` :28759、周锚 `_next_week_reset` :24344、日串 `_activity_day_key` :32226、赛季串 `_chunin_season_key` :21379；刷新函数如 `_refresh_daily_activity` :32230、`_refresh_hero_day` :17153、`_refresh_tower_period` :24318、`_refresh_family_boss_week` :33871。
- 2012：`role_day_arena` 每日场次表 + 每日 0 点 `RoleGiftTask` 清 `role_gift_step`。
- 复刻组：`character_copy_daily.reset_date`、`character_xiuxing_state.cycle_date`、`character_online_weekly.week_start`（SQL）。
- 玩法覆盖：活跃度/英雄副本/竞技场/忍者塔/帮会 Boss/签到/在线周奖/中忍赛季——**凡"每日/每周"字样的玩法皆此模式**。

### M6 玩法状态机（进度即枚举 + 推进器）
有过程的玩法都实现为显式状态机，状态存会话内存或 save：
- 任务 `QuestState`（ACTIVE→READY_TO_COMPLETE→…）+ 全局推进器 `_advance_original_quests`（在各玩法击杀/拾取/升级处统一打点，V223:56292、`QuestState` :1662）；

- 2012 的对应物是任务三段对话列 + `role_quest.is_finish/can_submit` 两状态列。

### M7 派生数值链与实时推导
战斗属性不走快照而走**单点聚合函数**：`_current_attack/_current_defence/...` 逐层叠加装备/宝石/被动/境界/宠物/罪恶/编辑器 buff（V223:47880-48095），客户端只收服务端权威值（`_send_authoritative_resources` :33992）。成就值、排行榜排名、VIP 等级（充值额派生+月卡衰减 :28041）都**实时推导不落库**。2012 的对照：二级属性由 `config_role_l2_attribute` 公式表换算、排行榜 `bill_*` 是定时快照表（5 分钟/每日重建）——"派生"与"快照"两种取法的分野。

### M8 概率 roll 工具族（千分率/百万分率/加权/保底）

- Nya：摆摊/拍卖/寄售/悬赏四本 hub 级 JSON（`_load_stalls` :10184、`_load_auctions` :10260、`_load_money_sell_listings` :10296、`_load_bounties` :10333）；交易双边 escrow 锁 `_complete_trade` :23826。

## 4. 专题：战斗结算的代际演进
