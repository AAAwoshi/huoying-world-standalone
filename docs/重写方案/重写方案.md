# 重写方案

> 配套文档：[技术栈方案](技术栈方案.md)（选型与理由）。
> 场景：单机、不跨机跨域、多账号多窗口、后台机器人无窗口；非商业、**禁止公开开服**。
> 证据来源：`spikes/rewrite-stack/**`、`spikes/godot-multiwindow/**`、`spikes/bot-capacity/**`、`docs/历史项目分析/**`（原始数据与复现脚本均在仓库内）。

---

## §0 目标与范围

**做什么**
1. 用现代技术栈重建**客户端 + 服务端 + 数据管线**，保留原有玩法、数值、美术与音频内容；
2. 单机可玩：**多账号多窗口**同时操作 + **无窗口机器人**后台模拟；
3. 把"没有规格书的 6 万行旧实现"变成**可回归、可回放、可交接**的工程资产。

**不做什么**（许可与定位决定）
- 不做公网运营、计费、反外挂、分布式承载、跨服；
- 不重做美术与数值（只做**离线转码**与格式迁移）；
- 不改协议**语义**（消息目录、顺序、权威规则）；但**编码层重写**，并保留旧编码作为可选兼容网关（详见 §3.7）。

**成功标准（可验收）**
1. 单进程内 N 个窗口 + M 个机器人稳定运行，无串号、无存档覆盖；
2. 协议**语义与原版一致**：消息级对拍 + golden packet 回归全绿；兼容网关下**原版 Flash 客户端可直连新服务端**；
3. 行为与旧实现**逐字段对拍**通过，差异全部落到"已知分歧台账"；
4. 任何一局都能**从命令日志重放**并复现（逐 tick 状态哈希一致）；
5. 新机器**解压即用**，无需管理员权限。

## §1 总体路线

```
                 ┌──────── Rules（纯函数、确定性、无 I/O）────────┐
                 │ 战斗/掉落/成长/公式/冷却/RNG(seed)              │
                 └───┬───────────────┬───────────────┬────────────┘
                     │               │               │
          ┌──────────▼──────┐  ┌─────▼────────┐  ┌───▼──────────────┐
          │ World（权威）    │  │ Client View  │  │ Bot Host         │
          │ 全量模拟 + 存档  │  │ 预测 + UI 状态│  │ = 无头 Client    │
          └──────────┬──────┘  └─────┬────────┘  └───┬──────────────┘
                     │               │               │
              ┌──────▼───────────────▼───────────────▼──────┐
              │ Host.App：命令队列 + 视图快照 + 线程/存储/传输 │
              └──────────────────────────────────────────────┘
                单进程（物理合并）｜逻辑边界由程序集规则强制
```

**四条原则**
1. **一个规则核心，多个宿主**：`Rules` 是纯函数库；服务端权威、客户端预测、机器人决策共用它。
2. **物理合并、逻辑不合并**：世界 tick 独占线程；跨线程只走**有序命令队列**；机器人与窗口**走同一条命令路径**。
3. **确定性 + 事件溯源**：固定步长、显式种子、单一写入者、逐 tick 状态哈希；状态 = 快照 + 命令日志。
4. **契约先行**：opcode/协议/内容 schema 全部机器可读、进 CI 快照；改错立即失败。

## §2 模块划分与依赖规则

| 程序集 | 职责 | 允许依赖 | 禁止 |
|---|---|---|---|
| `Core.Contracts` | 命令/事件/视图记录（可序列化）+ 内容 schema 类型 | — | 一切实现依赖 |
| `Core.Rules` | 纯函数：战斗、掉落、成长、公式、冷却、RNG | Contracts | **I/O、时钟、Godot、世界状态** |
| `Core.World` | 权威状态、tick、兴趣管理、命令应用、状态哈希 | Rules, Contracts | I/O、Godot |
| `Core.View` | 客户端视图模型：会话状态、本地预测、UI 状态机 | Rules, Contracts | **World** |
| `Host.App` | 组装：线程、队列、存储、传输、控制面 | 全部 | — |
| `Host.Client` | Godot 层：窗口、渲染、输入→命令、内容包 | View, Contracts | **World** |
| `Host.Bots` | 无头会话 + 行为树 + 场景脚本 | View, Contracts | **World** |
| `Tools.Content` | CLI：FFDec 编排、AMF3 读写、内容包构建与校验 | Contracts | — |
| `Tools.Oracle` | 与旧实现差分对拍 | Contracts | World |

**CI 机检**：`Host.Client` / `Host.Bots` 一旦引用 `Core.World` → 构建失败。这就是"用编译期规则替代进程边界"。

## §3 关键机制

### 3.1 确定性 tick（五条铁律）
1. 固定步长（20 Hz），世界只按 tick 序号推进；`Rules` 内**禁止读系统时钟**（时间作参数传入）；
2. 世界状态**只被 tick 线程**修改；
3. 状态容器用数组/有序结构，**禁止依赖字典遍历序**；
4. 每实体独立种子 RNG（沿用 `character_id * 7919` 口径），种子随日志落盘；
5. 每 tick 计算 `stateHash`，写入回放文件 ⇒ 分歧**精确定位到 tick**。

### 3.2 命令队列与视图快照（两个通道，别无其他）
- **命令队列**（多生产者 → Sim 单消费者）：人类输入、机器人决策、GM 动作**全部**走这一条；
- **视图快照环**（Sim 单生产者 → 多消费者）：每 tick 发布不可变快照，渲染与机器人只读；
- **Sim 线程永不阻塞**：不写盘、不等渲染、不等人——做不到这条，单进程方案不成立。

**契约边界清单（重构后真正需要"通信"的地方）**：

| # | 方向 | 契约内容 | 默认传输 | 频率 |
|---|---|---|---|---|
| **1** | `Host.Client` / `Host.Bots` / GM 面板 → `Core.World` | **命令**（`Core.Contracts` 里的可序列化 record） | 进程内无锁队列（可换命名管道/回环 TCP） | 输入级：每人 10–20 Hz |
| **2** | `Core.World` → `Host.Client` / `Host.Bots` | **视图快照 / 事件**（不可变） | 快照环（单生产者 → 多消费者） | 每 tick：20 Hz |
| **3** | `Core.World` ↔ `Host.App`（持久化） | **存档文档 + 命令日志**（快照/回放格式） | 异步写线程 + SQLite(WAL) | 每 N tick / 每关键事件 |

**外围（非运行时的）契约边界**（同样是"契约"，但不是消息）：

| 边界 | 契约 | 形态 |
|---|---|---|
| 内容管线 ↔ 运行时 | **内容包格式 + 内容哈希** | 文件（构建期产出） |
| 编辑器 ↔ 内容源 | **内容 schema**（JSON Schema） | 文件 |
| 测试 ↔ 实现 | **场景脚本 + golden packet + 期望状态** | 夹具文件 |
| 兼容网关 ↔ 原版 Flash 客户端 | **旧 wire 编码**（语义同契约 1/2） | TCP + 私有二进制帧 |
| 控制面 ↔ 外部工具（可选） | GM/遥测消息 | 本地 HTTP/WS |

**明确不通信的三处**：
- **窗口 ↔ 窗口**：一律不直连（输入广播是 `Host.Client` 内部的路由策略，不是模块间协议）；
- **`Core.Rules` ↔ 任何人**：它是**被调用的纯函数库**，不是通信方（服务端权威、客户端预测、机器人决策各自调用同一份规则）；
- **`Core.Contracts`**：纯数据定义，不参与通信。

**会新增边界的情况**：外置 Bot Host（1/2 变管道）、私人局域网联机（1/2 变 wire）、外部工具接入（控制面协议）、模组沙箱脚本（脚本 API 契约）。

**示例：双开两个账号互相交易，需要"窗口之间通信"吗？——不需要，也不允许。**

```
窗口A(账号A)                     Core.World（唯一权威）                     窗口B(账号B)
    │  命令 TradeInvite(B)            │                                        │
    ├────────────────────────────────►│ 校验距离/状态/等级                      │
    │                                 │ 事件 TradeInvited(from=A)               │
    │                                 ├───────────────────────────────────────►│
    │                                 │◄──────── 命令 TradeRespond(accept) ────┤
    │                                 │ 建立 TradeState（存在 World 里，唯一一份）│
    │  命令 TradeOfferPut(slot)       │                                        │
    ├────────────────────────────────►│ 更新同一份 TradeState                   │
    │                                 │◄─────── 命令 TradeSetMoney(n) ─────────┤
    │  命令 TradeConfirm()            │                                        │
    ├────────────────────────────────►│◄────── 命令 TradeConfirm() ────────────┤
    │                                 │ 同一 tick 内原子交换；失败则整体回滚     │
    │  事件 TradeCompleted            │  事件 TradeCompleted                    │
    │◄────────────────────────────────┼───────────────────────────────────────►│
    │                                 │ 写命令日志 + 两侧角色存档（原子）        │
```

现有实现已经是这个形状：【事实】`fake_flash_server.py:9027` 注释 `Atomic two-player trade state; inventory changes happen only on final confirm.`，交易状态挂在 hub 上（`:9314` `self.trades_by_character: dict[int, TradeState]`，`:9313` `trade_invites`），而 `multiplayer_backend.py` **完全没有 trade 引用** → 交易状态是运行时的、只在最终确认时落存档。

**结论**：双开交易走的是**通道 1/2（窗口 ↔ 世界）**，不是窗口 ↔ 窗口。把交易状态放进窗口、让窗口互相确认，会立刻带来状态分叉、竞态与不可回放三类问题。

### 3.3 传输与协议级回归
- `ITransport`：进程内直调（默认）/ 命名管道 / 回环 TCP；消息类型全部是**可序列化 record**；
- **协议级回归**（防的是"字节错"而非"功能错"）：
  - **A. golden packet 夹具**：抓录真实报文 + 期望响应，重放比对**响应字节**；
  - **B. 线协议机器人**：无头客户端走真实 socket，覆盖粘包/分片/超时/重连；
  - 判据：确定性报文逐字节相同；含随机的报文同种子字段级相同；`opcodes.json` 快照 diff 为空；变异帧不崩溃；差异必须进"已知分歧台账"。

### 3.4 存档与回放（事件溯源）
- SQLite(WAL) 单文件：`accounts` / `characters` / `snapshots(周期)` / `commands(追加日志)` / `content_pack` / `audit`；
- 崩溃恢复 = 最近快照 + 重放日志尾部 + **校验状态哈希** → 秒级恢复；
- 旧数据迁移：`accounts.json` + PBKDF2 口令哈希 + 每角色 JSON 文档**无损导入**；
- **禁止双写**：JSON 文档为权威、SQLite 只做索引与日志。

### 3.5 多窗口与机器人
- **多窗口**：单进程多窗口；**必须显式 `gui_embed_subwindows = false`**；每窗口绑定账号/会话/独立配置；布局档案（2×2 等）；非焦点降帧、隐藏零渲染但会话在线；可选输入广播；
- **机器人**：无头客户端核心 + 行为树 + 声明式场景脚本；种子 = `(characterId, 场景版本, 运行序号)`；**分批入场 + 错峰首 tick**（实测 800 个启动瞬态达 15.9 s、首轮延迟 20 s）；默认进程内，需要协议级回归时切外置进程。

### 3.6 内容与模组
- 内容源（文本）+ JSON Schema 校验 + 引用完整性（传送点→地图、掉落→怪物、商店→物品）→ **内容包（含内容哈希）**，三端共用；
- **模组 = 内容包 + 沙箱脚本 + 版本约束 + 热重载**，一等公民（魔改生态是本项目生命线）；
- 编辑器保留**覆盖层 + 历史快照**机制；**禁止工具直接改 `GameData.dat`**。

### 3.7 协议：重写什么、不重写什么

**什么是"消息契约"**：对**跨边界交换的消息**的共同约定——有哪些消息、每种带哪些字段（类型/单位/取值范围）、谁在何时发、谁权威裁决、失败怎么办、版本如何演进。
它**与编码格式和传输方式无关**：契约换了才叫改协议，编码/传输换了只是换实现。

| 概念 | 含义 | 本项目的例子 | 是否可变 |
|---|---|---|---|
| **契约（语义）** | 消息目录 + 字段 + 语义 + 权威规则 | `PLAYER_DAMAGE(1329)` 携带 目标ID/伤害/技能ID/命中时刻，服务端裁决 | **冻结**（它就是规格） |
| **编码（wire format）** | 契约如何变成字节 | 旧：`u16LE opcode + CodecUtil S-box + u16 checksum`；新：FlatBuffers/protobuf + 版本号 | **可重写** |
| **传输（transport）** | 字节如何送达 | 进程内队列 / 命名管道 / TCP 回环 | **可替换** |

**契约里必须写清的东西**：消息 ID 与名称、方向（C→S / S→C / 双向）、字段（名/型/单位/范围）、触发时机与频率上限、**谁权威（客户端声明 vs 服务端裁决）**、顺序依赖（如先 HELLO 再 LOGIN）、错误语义（拒绝/重试/断线）、版本兼容规则（新增字段可否忽略）、以及**一条真实报文字节样本**（即 golden packet 夹具）。

**在本项目里的物理形态**：`opcodes.json`（消息 ID 快照）+ `Core.Contracts` 里的可序列化 record（`MovePlayerCommand` / `MapChangedEvent` …）+ schema 定义 → **一份定义，生成 C# 类型、生成夹具、生成文档**，并进 CI 快照。

**把三件事分开**：

| 层 | 是否重写 | 理由 |
|---|---|---|
| **语义**（消息目录与行为） | **不重写** | 422 客户端 opcode / 122+164 服务端 opcode / 212 DTO / 78 handler 就是规格；重写它 = 重新发明 40 个玩法域（真正的工作量在语义，不在编解码） |
| **编码**（wire format） | **重写** | 推荐栈要重写客户端（D1）⇒ 字节兼容不再是硬约束；旧编码（S-box 固定置换 + 弱 checksum + **逐事件文本包**）既无安全价值，又是混战容量的直接瓶颈 |
| **旧编码** | **保留为可选兼容网关** | 码量小（AMF3 核心 ≈320 行 + 分帧），收益大：**原版 Flash 客户端可直连新服务端**，用作 M3/M4 的对照与保真基线（即 D10） |

**新编码的五条要求**：
1. **schema-first**（protobuf/FlatBuffers 或自研紧凑二进制）→ 生成 C# 类型，**不手写 DTO**；
2. **版本号 + 能力协商**，取代硬编码 `VERSION=79`；
3. **批量 + 增量**：每 tick 对每个接收者合并成一个包 —— 这直接解决混战 fan-out（全场互见 30k 包/s → 约 2k 包/s）；
4. **不假装加密**：S-box 是公开的固定置换，不提供任何安全性；要完整性用校验字段，要保密用真加密；
5. **认证修好**：不再传明文口令（旧实现 S7 缺陷）。

**"重写后的项目还需不需要协议"**：需要**消息契约**，不一定需要**网络协议**。
- 单进程内部：**命令队列 + 视图快照 + 可序列化 record** 就够了，不必"一切走线"；
- 线协议只在四种场合需要：① 外置 Bot Host / 拆进程；② 私人局域网联机；③ 外部工具（编辑器 / GM / 压测）；④ **回放与夹具的持久化编码**；
- 因此设计上保留 `ITransport` 与可序列化消息，但**不强行让进程内通信走线**。

**兼容网关的用法（推荐）**：新服务端同时实现 ① 新编码（自家客户端）② 旧编码（原版 Flash 客户端）。这样 M3 之前就能用**原版客户端**验证服务端，M4 的对拍也能做成"同一客户端、两个服务端"的形态——这是最省力的真客户端验证路径。

## §4 阶段计划

| 阶段 | 内容 | 产出 | 退出标准 |
|---|---|---|---|
| **M0 前置 spike**（并行 4 项） | ① Godot 单进程多窗口 ✅**已完成**；② C# 确定性；③ FlasCC `decodeData` 等价实现；④ SWF→帧表覆盖率 | 4 份 spike 结论 + 数据 | ①已通过（12 原生窗口 / 点击 12/12）；②两次运行状态哈希一致；③单类对照成功；④覆盖率 ≥95% 或有回退路径 |
| **M1 核心** | Contracts + Rules + 命令队列 + 状态哈希 + 回放骨架 | 无头可跑的核心 | headless 跑 10 万 tick，两次哈希一致 |
| **M2 世界与存储** | World tick + 兴趣管理 + SQLite 快照/日志 + 崩溃恢复 + 调试面板 | 可存可恢复的世界 | kill 进程后重放恢复，哈希与崩溃前一致 |
| **M3 客户端纵切** | 窗口 + 登录→进图→移动→战斗一条纵切 + 真实资产转码 | 单窗口可玩 | 帧率 ≥36 fps（目标 60）；显存/内存达标 |
| **M4 机器人与对拍** | 无头机器人 + 行为/场景 + Python oracle 对拍 + 协议级回归 | 机器人即回归 | 64 机器人 + 2 窗口稳定 30 min；tick ≤25 ms；对拍差异全部定性 |
| **M5 多窗口与内容** | N 窗口编排 + 内容包 + 模组热重载 + 引用完整性 CI | 多开可用 | 8 窗口一键启动；内容校验进 CI |
| **M6 容量与加固** | 压测（N/M 曲线）、内存预算、S1–S8 加固、异常兜底 | 可交付版本 | N=8 / M=2,000（目标）达标；崩溃恢复 <5 s |

> 依赖关系：M1→M2→M3/M4 可并行；M5 依赖 M3；M0-②③④ 必须早于 M3/M4 的对应部分。

## §5 验收体系（四层 + 两个专项）

| 层 | 手段 | 能抓住 | 抓不住 |
|---|---|---|---|
| 单元 | xUnit + 属性测试（`Rules` 是纯函数） | 公式、边界、分布、不变式 | 集成、内容、时序 |
| **对拍** | **Python oracle 差分**：同初始状态、同命令序列、同种子，逐字段比对 | 行为语义偏移 | 旧实现本身错的地方（需台账） |
| 回放 | 命令日志 + 状态哈希 | 非确定性、拆分漂移 | 渲染、手感 |
| 内容 | schema + 引用完整性 + round-trip 字节 diff + fuzz | 数据错误、解析器崩溃 | 数值是否好玩 |
| **专项 A：协议级回归** | golden packet + 线协议机器人 | **字节错**（帧/S-box/checksum/opcode/DTO 顺序） | 玩法语义 |
| **专项 B：保真对比** | 与原版 Flash 客户端逐帧截图对比 | 文本排版、滤镜、动画时序 | 主观体验 |

**已知分歧台账（R3）**：遗留实现里的 bug 也是"事实规格"（例：2.2.0"宣布即扣血"双扣 vs 2.2.3 授权-申报两段式；GM 默认口令 always-accepted）。**每条差异必须显式决定"复刻还是修正"，并写成断言锁住**。

### 5.1 Python oracle 对拍：定义与做法

**是什么**：把**遗留实现当作唯一权威规格**（oracle = 预言机/基准），让**新旧两套实现跑同一条场景脚本**（同初始存档、同命令序列、同随机种子），然后**逐字段比对可观测状态**——不一致的地方就是"重写走样"或"旧实现本身有 bug"。

**为什么本项目离不开它**：没有任何需求/设计文档，"正确"只能由旧实现定义；单元测试无法发明掉落公式、成长曲线、战斗结算规则这些**从未被写下来的知识**。

**怎么比（两级粒度）**：

| 粒度 | 做法 | 抓什么 |
|---|---|---|
| **黑盒（wire 级）** | 同一条报文序列喂给两套实现，比对**响应字节** | 协议层与路由差异（与协议级回归互补） |
| **白盒（状态级）** | 同一条**场景脚本**（`move / cast / use_item / loot / wait N ticks / save`）驱动两侧，每步导出**状态快照 JSON**（HP/MP/坐标/背包/经验/任务/掉落/存档字段） | **玩法语义**差异（数值、结算顺序、状态机） |

**前提（缺一则对拍结果全是噪声）**：确定性——固定步长、显式种子（沿用 `character_id * 7919` 口径）、不读系统时钟；两侧的"初始存档"必须字节一致。

**产出三样东西**：
1. **差异报告**：逐字段标注 相同 / 不同（含两侧取值）；
2. **已知分歧台账**：每条差异显式决策 **复刻（bug-for-bug）还是修正**，并写成断言锁住——例如 2.2.0"宣布即扣血"双扣 vs 2.2.3 授权-申报两段式，只能选一个；
3. **回归夹具**：脚本 + 种子 + 期望状态，进 CI。

**不要误解的两点**：
- **对拍通过 ≠ 正确**，只等于"与旧实现行为一致"；旧实现本身有 bug（S1–S8）与平台怪癖（GBK、非规范 AMF3 字符串、zlib 级别），这些必须靠台账显式裁决；
- **对拍不能替代单元测试**：它告诉你"哪不一样"，不告诉你"为什么"；定位仍需 `Rules` 层的纯函数单测与状态哈希。

**落地顺序（建议）**：先做一条**纵切**——登录 → 进图 → 移动 → 一次战斗结算 → 存档往返；跑通后再按玩法域扩展（40 个域按优先级排）。
**已知的工程前提**：遗留服务端已能被隔离存档启动（`spikes/bot-capacity/bench_bots.py` 已验证）；但**驱动 oracle 侧需要能完成登录/进图的客户端**——无头机器人目前只跑 AI tick、不进世界，因此对拍夹具需要线协议机器人或补齐进程内引导流程（M4 的工作）。

## §9 附：50–100 人同屏混战的容量评估（含一次失败的实测）

### 9.1 实测到什么、没实测到什么

| 项 | 结果 |
|---|---|
| ✅ 已实测 | 单进程机器人 **AI tick 成本 0.27–0.42 ms/次，且与规模无关**；400 个活跃机器人 = **44.9% 单核**、延迟 5.4 ms（`spikes/bot-capacity/bench_bots.py`） |
| ❌ 未能实测 | **真实同屏混战**。无头机器人只跑 AI tick，**没有完成登录/进图**（10 个机器人仅 1 个 session 进入世界，10 秒仅 8 个出站包）→ 拿不到真实的"攻击→广播→客户端"链路数据 |
| ⚠️ 关键发现 | 遗留实现的 `broadcast_visible` **会跳过机器人之间的发包**（`fake_flash_server.py:9657-9661`：`if source.server_simulated and peer.server_simulated: continue`）→ **"机器人混战"在现有实现里几乎不产生玩家间流量**，用它评估混战会严重低估 |

**要拿到真实数字，必须做"线协议机器人"**（真的完成 HELLO→LOGIN→进图→战斗，走 socket），即《重写方案》§5 的专项 A/B——这是 M4 的工作。

### 9.2 服务端容量模型（按 100 人同屏、全部互见）

```
出站包/s ≈ N × 每人每秒事件数 × 视野内人数
N=100、每人 3 事件/s（移动+技能+状态）、全场互见(≈99) → 100×3×99 ≈ 29,700 包/s
若做 AOI（视野内平均 30 人）           → 100×3×30 ≈  9,000 包/s
```

| 实现 | 每包成本（编码+分发） | 30k 包/s 的 CPU | 判定 |
|---|---|---|---|
| 遗留 Python（单进程、GIL） | ~20–50 µs | **0.6–1.5 核** → 超单核预算，会掉 tick | **50–100 混战"能跑但吃紧"**，必须做 AOI + 批量打包 |
| 目标 C#（编译、无 GIL、批量编码） | ~2–5 µs | **0.06–0.15 核**（6–15%） | **轻松**；瓶颈回到确定性 sim（100 实体约 1–3 ms/tick，占 20 Hz 预算 5–15%） |

### 9.3 客户端容量（同屏 100 个角色）

- 实测渲染吞吐：**图集化后 24,000 精灵 = 20 draw call**；60 fps 预算 ≈8,000–10,000 精灵 item（`spikes/godot-multiwindow/bench2.ps1`）；
- 100 个角色（帧动画）+ 名字标签 + 血条 ≈ **几百个 draw item** → **远未到瓶颈**；
- 真正的风险是**技能特效**（Flash 滤镜/遮罩语义）与**大量富文本标签**，需在保真 spike 里单独量化。

### 9.4 结论与必做项

**结论**：**目标 C# 架构下 50–100 人同屏混战属于舒适区间**；**遗留 Python 实现在全场互见的情况下会吃紧**，但加上 AOI 与批量打包后可用。

**必做（缺一不可）**：
1. **AOI/兴趣管理**：只广播给视野内的玩家——这是把 O(N²) 降为 O(N×k) 的唯一有效手段；
2. **批量/增量打包**：每 tick 对每个接收者合并成一个包，而不是逐事件发文本包（遗留实现是逐事件）；
3. **分级频率**：移动 10–20 Hz、状态/血条 5–10 Hz、技能特效按需；
4. **单 tick 预算保护**：设每 tick 发包上限，超限合并/丢弃（宁可少发，不可掉 tick）；
5. **前置验证**：M4 必须用**线协议机器人**实测 100 人同屏的包/s、CPU、tick 时间与延迟分布。

```
① 抽契约 → ② 录场景 → ③ 写实现 → ④ 对拍 → ⑤ 差异裁决 → ⑥ 锁断言 + 进 CI
```

| 步 | 做什么 | 产物 | 完成标志 |
|---|---|---|---|
| ① 抽契约 | 从旧实现里读出该玩法涉及的消息、字段、权威规则、频率 | `opcodes.json` 条目 + 契约说明 | 契约条目可复核（指向旧代码行号） |
| ② 录场景 | 用旧实现跑一条脚本（登录→该玩法→存档），导出每步状态快照 | 场景脚本 + 期望状态 JSON | 脚本可重复运行且结果稳定（确定性） |
| ③ 写实现 | 在新栈实现（`Core.Rules` 纯函数 + `Core.World` 状态机） | 代码 + 单测 | 单测通过；不引入 I/O/时钟 |
| ④ 对拍 | 新实现跑同一脚本，逐字段比对 | 差异报告 | 差异清单完整 |
| ⑤ 裁决 | 每条差异决定 **复刻 or 修正**，记录理由 | 已知分歧台账 | 无"未裁决"项 |
| ⑥ 锁断言 | 把结论写成断言/夹具 | 测试 + 夹具 | 进 CI，回归时自动拦住漂移 |

**为什么必须六步**：跳过 ① 会漂移，跳过 ② 无法验证，跳过 ⑤ 会出现"修 bug 和引入 bug 分不开"。

### 11.3 四类典型工作的模板

| 类型 | 流程差异 | 完成标志 |
|---|---|---|
| **玩法域迁移**（掉落/成长/任务…） | 走 §11.2 全流程 | 对拍通过 + 台账无未决项 |
| **客户端 UI 迁移**（背包/商店窗口…） | 多一步**保真对比**：原版截图 vs 新实现截图（结构 + 像素） | 截图差异有结论（可接受/已替代） |
| **资产管线**（SWF→图集） | 批量跑 + 覆盖率报告 + 失败项回退策略 | 覆盖率 ≥95%，失败清单有处置 |
| **遗留缺陷处置**（如 S5 解锁码） | **先写 characterization 测试锁住"现状"**，再决策修正，最后更新台账与断言 | 现状被锁 → 修正被记录 → 断言更新 |

### 11.4 CI 门禁（每次提交都跑，任一失败即拒）

1. **构建**：全部程序集 + Godot headless 导出；
2. **依赖规则机检**：`Host.Client`/`Host.Bots` 不得引用 `Core.World`；
3. **单测 + 属性测试**；
4. **协议级回归**：golden packet 逐字节 + `opcodes.json` 快照 diff 为空；
5. **回放回归**：固定种子 + 命令日志 → 逐 tick 状态哈希一致；
6. **内容校验**：schema + 引用完整性 + AMF3↔JSON round-trip 字节 diff。

### 11.5 提交与评审规范

- **契约变更单独提交**（便于回滚与审阅），并在提交信息里写明：影响的契约、对拍结果、回放哈希；
- **"无证据不合并"**：每个改动必须附**复现命令 + 输出**（本仓库 `spikes/` 的既有脚本就是范例）；
- PR/提交模板四问：① 改了哪个契约？② 对拍结果如何？③ 回放哈希是否一致？④ 有哪些未验证项？
- **禁止直接改夹具的期望值**：期望值只能通过 §11.2 第⑤步的裁决流程修改，并留下台账记录。

### 11.6 AI 协作规范（本项目特有，且有历史教训）

历史证据：姬水县人版留下 **42 章交接文档 + 427 个 verify 脚本 + 33 份数据备份**（AI 长会话的产物），嗯哼版有 169 个编号小节——**优点**是"每改动带验证与备份"，**缺点**是没有统一测试框架、靠人肉 verify、结论散落在文档里。

**规则**：
1. AI 只能通过"**契约 + 测试 + 夹具**"改代码——不接受"看起来对"；
2. 每次 AI 改动必须附**复现命令与证据**，并说明**未验证项**；
3. AI **不得**修改 `fixtures/` 的期望值与 `opcodes.json`（除非走裁决流程）；
4. 长任务必须**分段落盘**（本项目已出现两次"单轮写太长导致中断"的实例）；
5. 每个里程碑结束时更新**决策记录**（见 §11.8）。

### 11.7 里程碑交付节奏

每个 M 阶段结束产出**三样**：① 可运行产物（不是截图）；② 该阶段的报告（指标 + 未验证项）；③ 更新的契约与夹具。
**Definition of Done（单块工作）**：代码 + 单测 + 对拍/回放通过 + 契约条目更新 + 台账无未决项 + 复现命令。

### 11.8 决策记录（ADR）与台账

- **ADR**：每个架构/选型决策一页（背景、选项、决定、后果），避免"为什么这么设计"丢失；
- **已知分歧台账**：每条"复刻 vs 修正"的裁决（这是本项目最重要的资产之一）；
- **spike 结论**：每个前置 spike 一页（方法、数据、结论、是否放行后续）。
